Update a custom dashboard by ID. Same `{dashboard, metadata}` envelope and same panel/query shape as create_dashboard (full replacement): panels use `layout` and `visualization`; query panels also use `queries`; section and markdown panels do not. CSV-backed table/chart panels use a `csv` object and dashboard-level `csv_datasource` instead of remote `queries`. Non-section panels may omit `version` and default to `version: 1`; logs panels must explicitly set `version: 1`, and section panels stay versionless. A logs visualization also needs `logs_config: {columns: [...]}` with one or more of `timestamp`, `reason`, `severity`, `kind`, `service`, or `body`, and exactly one logs query of type `log_ql` or `log_raw`. Each query uses `name`, `type`, `query_type`, `telemetry`, `expr`, and `legend: {type, value}`. Legend `type` is `auto` or `custom`; use `auto` unless an explicit label is needed. Use `promql` for metrics, `log_ql` or `log_json` for log charts, `log_ql` or `log_raw` for raw log panels, and `trace_ql` or `trace_json` for traces; `logs` is a telemetry value, not a query type. For `query_type: "log_raw"`, use `telemetry: "logs"` and a non-aggregate JSON pipeline in `expr`. Every `log_json` expression must be a JSON pipeline with an aggregate stage. For `log_json` line, timeseries, or bar panels, include exactly one aggregate with a time window; grouping by service or environment does not replace the window. Readonly system dashboards return an error.

Use this only to restructure most of a dashboard. To add, edit, remove or move individual panels, use patch_dashboard: it sends only the changed panels, while this tool must re-send every panel exactly, and any drift silently changes or drops panels. Pass the existing dashboard id; do not call create_dashboard to refine a dashboard that already has an id.

For `log_json` line, timeseries, or bar panels, use a `window_aggregate` stage with a `window`; a plain `aggregate` stage does not satisfy the API's timeslice requirement.
