Replace an alert rule's evaluation configuration. First use get_alert_config or get_entity_alert_rules to retrieve the rule and verify entity_id. Pass the complete typed configuration in alert_rule; primary_indicator and expression_args are required, and partial evaluation updates are unsafe. Clients cannot set algorithm; the backend derives it from expression. Static (default): expression is plain arithmetic over indicators, or omitted; condition, alert_condition, and eval_window are required, eval_window 0-60 minutes. Adaptive: expression is exactly adaptive_std_cmp(<primary_indicator>, sensitivity, window), for example adaptive_std_cmp(latency, 3, 1h); sensitivity is a number (the dashboard uses whole numbers 1-10, default 3) and window is the baseline length (the dashboard offers 1h, 1h30m, 2h, 2h30m, 3h). It is classified as adaptive but evaluated as a threshold on the adaptive bounds; condition, alert_condition, and eval_window are optional, supplied values are kept and omitted ones default to "expr > 0", "count_true(result) >= 1", and 1. Preserve properties and grouping settings when they should not change. Use patch_alert instead for promotion, pause, mute/unmute, descriptions, runbooks, annotations, and query_mode. PUT may soft-delete and recreate the rule, so always use the returned replacement ID for subsequent actions. Notification routing belongs to the alert group, not the rule. Refine an existing rule with update_alert (full replace) or patch_alert (partial: pause, mute, metadata) and keep its rule ID; never create a duplicate with create_alert. Dry-run an expression with validate_alert_expression before saving. Grammar, units, validation behaviour and rule templates: read last9://reference/alerting.
