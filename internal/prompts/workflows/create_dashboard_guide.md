# Create a dashboard

Use this workflow for a net-new dashboard or to plan a targeted edit. It takes no prompt arguments; use the user's requested scope, purpose and time window. Only call tools available in this session. If discovery, validation or writes are unavailable, explain what remains unverified or unsaved; do not claim completion. A name-only request creates an empty dashboard with `panels: []`, without inventing queries.

1. Discover the data. Use `list_datasources` to select the intended metric datasource, `prometheus_label_values` with `label: "__name__"` to find metrics, and `prometheus_labels` plus `prometheus_label_values` to discover their labels and values. Keep discovery scoped to the panels requested; use a supplied service name as given. Confirm metric type and unit from instrumentation documentation or the user; names and suffixes alone are not proof of counter semantics, and the current discovery tools do not supply authoritative metric types. For log and trace fields use `get_log_attributes_for_pipeline` and `get_trace_attributes_for_pipeline` with the scoped filter pipeline. Never invent tenant metrics, label names or field paths.

2. Lay out the dashboard on a 12-column grid using `layout: {x, y, w, h}` in grid units, with nonnegative coordinates and positive sizes, `x + w <= 12`, and no overlap. Start sections at x=0, w=12, h=1. Use three w=4 summary panels (h=4), two w=6 trends (h=8), and full-width w=12 tables or logs (h=8) as starting sizes, adjusting to content. Advance y by the tallest panel in the row. Use a versionless `visualization: {type: "section"}` panel for each heading; sections and markdown panels have no queries. Put overview before endpoint/service breakdowns and supporting logs/traces.

3. Choose panel types by question: `stat` for one value per series, `timeseries` for a trend, `bar` for category comparisons, `table` for ranked rows, `logs` for raw log entries, and `markdown` for context. Use `visualization.type`, never panel-level `type` or `gridPos`. Non-section panels use `version: 1`. A logs panel requires `visualization.logs_config.columns` (e.g. timestamp, severity, body), exactly one logs query of type `log_ql` or `log_raw`, and explicit version 1. Aggregate log charts use `log_json`; trace queries use `trace_json` or `trace_ql` in a suitable table or chart.

4. Build queries from discovered data. Each query has `name`, `type` (instant or range), `query_type`, `telemetry`, string `expr`, and `legend: {type: "auto", value: ""}` unless a custom legend is needed. Use `promql` with metrics, log query types with logs, and trace query types with traces. Choose counter, gauge, histogram or precomputed-quantile semantics explicitly; distinguish rollup window from evaluation step. Use variables for reusable scope and dependent label matches, resolving them before test queries. Use `query_guide` for query semantics and `dashboard_examples` for worked payloads; both are MCP prompts and reference resources. Read `last9://reference/logjson` and `last9://reference/tracejson` for pipeline syntax.

5. Validate before requesting approval. Check the complete `{dashboard, metadata}` candidate against the create tool schema, then call `validate_dashboard` with the full inner dashboard object as `dashboard_definition` (not the envelope), plus required `start_time_iso` and `end_time_iso` in RFC3339. Do not also pass `dashboard_id`. Resolve relative times with `get_current_time`. Its window must be positive and at most 24 hours; for longer requests validate bounded slices and disclose coverage. Optional `variables` are scalar overrides, not arrays. Inspect every target and lint finding, not just top-level success. Fix invalid queries and unresolved variables; disclose no-data results and execution failures. `unsupported_execution` is not a passing query check. The validator does not prove rendering parity: it uses the default metric datasource, visualization-based query mode and simplified variable/interval defaults.

   Then run each panel's query using the existing tools over the requested window: `prometheus_range_query` for range metric queries (explicit start/end and selected datasource; this tool exposes no step argument), `prometheus_instant_query` for instant metric queries (`time_iso` at the window end, with a rollup in the expression when needed), `get_logs` with `logjson_query`, and `get_traces` with `tracejson_query` for log and trace JSON pipelines (explicit start/end). Resolve dashboard variables and built-in intervals first; execute every target of a multi-query panel. These tools do not accept LogQL or TraceQL: use a semantically equivalent JSON pipeline and change the candidate to that tested query type, or report that validation is blocked. Skip remote queries only for section, markdown and CSV panels; inspect their content locally. Report panel, resolved query, window, datasource/index, units and outcome. Do not describe partial results as complete validation. Future: query_panel replaces this separate panel-check step once #475 lands; it is not available yet.

6. Approve the concrete result. Present the candidate layout, queries, variable defaults and per-panel validation outcomes, including any unresolved limitations, before asking the user to approve saving. If saving this concrete change is already authorized, proceed within that scope. Do not save a query that failed validation as if it passed.

7. Save once with `create_dashboard`, passing `{dashboard, metadata}`. Keep the returned dashboard.id. For an existing id, first read with `get_dashboard`, prepare and validate the resulting full candidate, then use `patch_dashboard` with `id` and ordered `ops`: `add_panel` takes a full panel and optional zero-based index; update_panel takes panel_id and fields; `remove_panel` takes panel_id; `move_panel` takes panel_id and index; `set_title` takes title; `set_variable` takes a variable object keyed by target. Use ids from the read. Never replace the whole dashboard for a small edit; `update_dashboard` is only for an intentional broad restructure. After an uncertain create outcome, check by name with `list_dashboards` before retrying.

8. Read back with `get_dashboard` using the saved id. Compare stored panels, queries, layout and variables with the approved candidate; report dropped or unrestored fields rather than claiming they landed. Inspect patch results' not_stored and not_removed fields. Keep refining the same id with `patch_dashboard`, never a second create.
