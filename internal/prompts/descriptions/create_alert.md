Create an alert rule in an existing Last9 alert group. The rule is ALWAYS created disabled (a draft), whatever is_disabled says. Start with recommend_alert_config, then discover and verify the entity, KPI/query, unit, and label dimensions. Pass entity_id separately and the complete typed rule body in alert_rule. Bind primary_indicator and expression_args to real KPIs owned by the entity; do not invent IDs. Each expression_args key must be the exact name of the KPI it binds, not a placeholder such as x, and primary_indicator and expression use those names. Clients cannot set algorithm; the backend derives it from expression. Static (default): expression is plain arithmetic over indicators, or omitted; condition, alert_condition, and eval_window are required, eval_window 0-60 minutes. Adaptive: expression is exactly adaptive_std_cmp(<primary_indicator>, sensitivity, window), for example adaptive_std_cmp(latency, 3, 1h); sensitivity is a number (the dashboard uses whole numbers 1-10, default 3) and window is the baseline length (the dashboard offers 1h, 1h30m, 2h, 2h30m, 3h). It is classified as adaptive but evaluated as a threshold on the adaptive bounds; condition, alert_condition, and eval_window are optional, supplied values are kept and omitted ones default to "expr > 0", "count_true(result) >= 1", and 1. Put responder context in properties: description, runbook as {"link":"https://..."}, annotations such as owner, service, environment, summary, dashboard, logs, traces, and escalation policy, and query_mode (builder or code). Annotation templates may reference label values as $labels.<name> and the sample value as $value, each wrapped in double curly braces. Notification routing is configured on the alert group, not the rule. Promote the draft with patch_alert is_disabled=false only after the user confirms. Create once and keep the returned rule ID; to change an existing rule use update_alert (full replace) or patch_alert (partial: pause, mute, metadata) and never create a duplicate. A rule_name the alert group already uses (case-insensitive) is refused without creating anything, naming the existing rule's id. Returns the created rule ID and a link to Alerting. Dry-run an expression with validate_alert_expression before saving. When the user wants an alert on a Discover chart (service or exceptions page), use create_alert_from_chart; custom dashboard panels are not covered by it, so bind create_alert to a KPI of the alert group instead; do not switch to create_alert to inject custom PromQL into a chart-derived alert — explain that constraint instead.
